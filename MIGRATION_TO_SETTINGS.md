# Переход с GyverPortal на Settings

Этот проект сейчас использует `GyverPortal` напрямую в `Portal.ino` для:
- многостраничного UI (`/`, `/settings`, `/connect`, `/ota_update`)
- OTA-виджетов
- обработчиков click/update/form

`Settings` можно использовать как рекомендуемую библиотеку для конфигурации, но для полного паритета по UI потребуется переработка веб-части.

## Что сделано в этом коммите

1. Подготовлен флаг миграции `USE_SETTINGS_UI` в основном скетче.
2. Добавлен файл с шагами миграции и картой соответствий полей.
3. Зафиксирована стратегия поэтапного перехода без потери текущего поведения световых режимов.

## Карта полей

- `ssid` -> Wi‑Fi SSID
- `pass` -> Wi‑Fi password
- `useLocalAddress` -> использование mDNS имени
- `localAddress` -> mDNS host
- `powerOn` -> состояние питания
- `globalBrightness` -> яркость
- `currentMode` -> текущий режим

## Поэтапный план

1. Подключить `Settings` и вынести структуру параметров в единый объект конфигурации.
2. Перенести форму `/connect` в форму Settings (минимальный рабочий UI).
3. Перенести `/settings` (яркость/режим/локальный адрес).
4. Заменить обработчики `ui.click*` на колбэки Settings.
5. Отдельно вернуть OTA-обновление (или через встроенный OTA-модуль, или отдельный endpoint).
6. Удалить зависимость от `GyverPortal` после прохождения smoke-тестов.

## Риски

- API `Settings` отличается от `GyverPortal`; требуется ручная адаптация callback-логики.
- OTA-блок из `GyverPortal` нельзя перенести 1:1 без проверки доступных модулей.
- Понадобится тест на реальном устройстве (Wi‑Fi connect/AP fallback/перезагрузка/EEPROM).
